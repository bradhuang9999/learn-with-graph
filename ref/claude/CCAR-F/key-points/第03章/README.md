## 綜合練習

設想儲存庫含 `apps/web/`、`packages/api/` 與 PR 審查管線：

1. 原作者把全團隊的 API 契約測試命令寫在個人 `CLAUDE.md`，新同事卻未遵循。先查什麼、應放哪裡？
2. 團隊每月才執行發布審查，流程需讀數百個檔案，主會話只要結論。選常駐指示、技能，還是路徑規則？`context: fork` 須補哪些資訊？
3. `.test.tsx` 分散於 `apps/` 與 `packages/`；只在這些檔案接觸時載入共同 fixture 慣例。規則如何寫、如何測到確實是條件載入？
4. 單檔 `validateDate` 空值 bug 已有失敗測試；另一任務是更換 45 個檔案的驗證函式庫。兩者選什麼模式？後者執行時若發現舊錯誤格式有隱藏使用者，怎麼辦？
5. 資料遷移把 `age: null` 轉成 `0`，且報表總數偏大。下一輪應提供哪些證據？兩症狀要分開還是合併回饋？
6. PR 審查在第二次提交後重貼同一缺陷；輸出還缺 `structured_output.findings`。能以「沒有新發現」繼續發布嗎？

**答案要點：**

1. 查團隊是否能取得規則與目前會話是否載入；共享要求放版控中的專案或適用目錄指示，必要時用路徑規則。
2. 用按需技能；`context: fork` 適合隔離冗長探索，但技能須自含任務、輸入路徑、範圍與回傳形式，不能假定繼承對話。
3. 在 `.claude/rules/` 寫 `paths: ["**/*.test.tsx"]`；用匹配／不匹配檔案各自開新會話並看 `/context`，避免同會話先載入後誤判。
4. 前者直接修正並驗證；後者先規劃、審核契約與回退。隱藏使用者使假設失效時，先說明影響；若多個後續步驟受影響，停止擴大修改並重新規劃。
5. 提供失敗輸入、預期 `null`、實際 `0`、報表錯誤與失敗測試；同根因的兩個症狀應一併描述，修正後跑回歸測試。
6. 不能。缺必要業務欄位是失敗，不是零項發現；傳入先前發現與既有測試，發布器按目前差異定位並做去重。
