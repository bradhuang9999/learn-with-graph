# 第 4 章｜品質、可靠性與規模化處理

你可能已經能讓 Claude 完成一份審查或文件擷取；本章要處理的是它進入團隊流程後的問題：如何減少「看起來有道理」的誤報、穩定輸出格式、區分可重試與不可重試的錯誤，以及在大量請求或多人協作時維持品質。

本章不是一條要求每個專案照做的固定管線，而是一組依失敗類型選用的設計方法。官方考綱以 4.1–4.6 分開考察；閱讀時可把它們放進兩個並行的工作情境。

| 情境中的問題 | 先學的機制 | 對應節 |
|---|---|---|
| PR 審查意見太多，工程師不再信任 | 明確報告與排除標準，辨認誤報 | [4.1 精確度](<4.1 用明確標準提高精確度並減少誤報.md>) |
| 標準已寫，邊界案例仍判得不一樣 | 給有代表性的輸入／期望輸出，教判斷邊界 | [4.2 少樣本](<4.2 以少樣本範例改善一致性與品質.md>) |
| 發票擷取結果有時是一段文字，有時漏欄位 | 用工具輸入或 JSON Schema 穩定輸出形狀 | [4.3 結構化輸出](<4.3 用工具呼叫與 JSON Schema 強制結構化輸出.md>) |
| JSON 合法，金額卻與來源不符 | 分層驗證、給具體回饋、只重試有望修正的失敗 | [4.4 驗證與重試](<4.4 為擷取品質設計驗證、重試與回饋迴圈.md>) |
| 每日上千份摘要明早才用，但 PR 安全審查必須即時 | 依延遲與成本要求選同步或非同步批次 | [4.5 批次處理](<4.5 設計有效率的批次處理策略.md>) |
| 產生程式碼的代理自審，漏掉跨檔權限漏洞 | 用獨立實例與逐檔／跨檔兩輪審查 | [4.6 多實例審查](<4.6 設計多實例與多輪審查架構.md>) |

## 章末整合：先判斷失敗在哪一層

若審查代理回報大量風格問題，先修報告標準，不是先加重試。若擷取結果 JSON 欄位齊全卻把不存在的總額編出來，應檢查來源可得性與業務驗證，不是只加 schema。若同一代理反覆檢查自己的改動仍漏跨檔漏洞，需換獨立審查視角，不是只要求「更仔細」。如果問題主要是每天大量、可延後的獨立請求，批次才可能是成本工具；它不會自動修正前述品質問題。

讀完後，選一個你熟悉的 Claude 工作流，依序問：錯誤是判準、輸出形狀、內容正確性、處理時效，還是審查視角？能說清失敗位置，才知道本章哪個機制值得採用。

### 綜合練習：採購報銷上線前的取捨

一家實驗室把 Claude 接入採購報銷與程式碼審查。團隊觀察到下列現象，想在有限工程時間內先改最關鍵的地方：

| 觀察 | 目前資料 |
|---|---|
| 一批 800 張收據隔天報表才用；另有 25 張屬當日付款放行，十分鐘內需結果 | 每張可獨立處理，但現行流程全部同步呼叫 |
| 收據 A 明印**完整品項清單** 120、80、稅 10、總額 215，並註明無折扣、運費或其他費用；收據 B 的下半頁缺失，只看得到兩筆品項 | 擷取器對 A 回 `stated_total=215`，對 B 把缺失總額填成 200 |
| 擷取器有時回一段散文，有時回 JSON；即使 JSON 合法也可能把欄位填錯 | 下游程式偶爾解析失敗，偶爾收下錯值 |
| PR 審查代理反覆回報變數命名，卻漏掉跨兩個模組的重複付款路徑 | 審查仍沿用產碼的同一會話 |

先不要看下方解析。請回答：A、B 應該各標什麼狀態？兩者是否有任一筆值得直接讓模型重試；如果沒有，什麼情況才值得？800 張和 25 張各選哪種處理方式、為何？要讓程式穩定接收資料，先改哪個契約、而它仍無法保證什麼？PR 審查要改哪兩個互不相同的設計面？最後指出至少兩個看似省事、其實會惡化問題的作法。

### 參考解析

1. A 的完整品項與已知稅費可算出 210，與印刷總額 215 衝突；若模型確實讀到原文，就應保留 `stated_total=215`、`calculated_total=210`、`conflict_detected=true`，交人工或依業務規則處理，**不為了湊一致而重試成 210**。B 沒有總額來源、品項與稅費也無法確認完整，應標 `stated_total=null`、`calculated_total=null`、`conflict_detected=null`（無法比較）並要求補頁；不能把 B 目前可見的品項當成完整總額。兩者都不適合直接重試。只有模型把原文已存在的值讀錯，且驗證器能指出具體錯誤時，才值得有限重試。對照 [4.4](<4.4 為擷取品質設計驗證、重試與回饋迴圈.md>)。
2. 800 張可考慮非同步批次並預留逐筆失敗補送；25 張是付款放行閘門，應同步處理並定義逾時失敗路徑。批次折扣不能代替交付時限；對照 [4.5](<4.5 設計有效率的批次處理策略.md>)。
3. 先用 [4.3](<4.3 用工具呼叫與 JSON Schema 強制結構化輸出.md>)的工具輸入或受約束 JSON 穩定欄位與型別，再檢查停止原因與來源語意；Schema 不會替你補 B 的缺頁，也不會判 A 的 215 是否可入帳。
4. 先按 [4.1](<4.1 用明確標準提高精確度並減少誤報.md>)排除命名偏好等非缺陷，再用 [4.2](<4.2 以少樣本範例改善一致性與品質.md>)的正反例教有爭議的報告邊界。另依 [4.6](<4.6 設計多實例與多輪審查架構.md>)用不含產碼歷史的獨立審查實例，並分逐檔與跨檔兩輪；只在同一會話多問一次「再仔細看」不會移除生成脈絡。

錯誤作法包括把 B 的空值填成品項加總、把 A 的來源總額改寫成 210、把當日放行改批次、把風格偏好當缺陷，或把同一會話的第二次呼叫誤當獨立審查。每項錯誤都把不同層的問題混成一種解法。
