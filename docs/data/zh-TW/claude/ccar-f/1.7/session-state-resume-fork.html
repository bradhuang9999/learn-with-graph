原始考綱

知識要求

  • 以 --resume <session-name> 指定並續接先前具名的對話。
  • 使用 fork_session 從共同分析基線建立獨立分支，探索不同做法。
  • 程式碼修改後續接工作階段時，必須告訴 Agent 先前分析過的檔案有哪些變更。
  • 當既有工具結果已過時，用結構化摘要開新工作階段，比直接續接舊上下文更可靠。

技能要求

  • 使用具名工作階段與 --resume，跨次工作延續指定的調查。
  • 使用 fork_session 從共同程式庫分析基線建立並行探索分支，例如比較兩種測試或重構策略。
  • 先前上下文大致有效時選擇續接；先前工具結果已過時，則以注入摘要的方式重新開始。
  • 告知續接的工作階段哪些檔案具體變更，使 Agent 定向重新分析，而非要求全面重查。

要點筆記

舊觀察是否仍可信，決定如何延續

工作階段(Session)保存對話、先前工具結果與當時的分析脈絡，卻不會凍結檔案或外部系統。隔天恢復工作時，主要判準不是哪種方式最省文字，而是舊觀察對目前環境是否仍有效。沿用過時工具結果，可能讓代理在錯誤前提上作出看似有理的後續修改。

續接、分叉、重開各解決不同問題

情況 選擇 必要檢查
原分析大致仍有效，要沿原問題繼續 用考綱的 --resume <session-name> 續接具名會話 告知自上次以來的變更，重讀受影響檔案或資料
要從同一份已核實的分析基線比較兩種方案 用 fork_session 建立後續獨立的會話分支 分支會話互不共享後續發現；外部工作目錄不會自動隔離
大量舊工具結果已失效，續接會使新舊資料混雜 新開會話，注入結構化摘要 保留目標與仍有效的約束，重新建立現況證據

摘要至少交代原始目標、已核實事實及來源、仍有效的限制、已知變更、待重新查證的問題與下一步。它不是將舊對話全文重貼；要清楚區分「可沿用的決策」和「依舊版本檔案得到的觀察」。fork_session 也不是 1.3 的子代理交接捷徑：一般子代理仍須在提示中取得必要事實。

變更後如何恢復可靠的基線

假設週五會話 auth-review 讀過 auth.ts，週一驗證函式已被別人修改。即使使用 --resume auth-review，也要明確指出變更：「auth.ts 的驗證函式與相關測試已更新；先重讀再沿原計畫執行。」接著找出哪些舊結論依賴這些檔案，針對受影響處重新驗證；變更範圍不明時再擴大檢查。若整個認證流程已重寫，舊工具輸出大部分失效，就以摘要新開會話，比續接長篇過時記錄可靠。

若檔案未變，團隊想比較「小幅修補」與「抽換驗證模組」，可從同一基線分出兩條會話，各自提出風險與測試需求。但分叉的是對話歷史，不是檔案系統：兩條分支若在同一工作目錄同時改 auth.ts，仍會互相干擾；實際試作須另行隔離工作樹或環境，並在比較前核對各分支所讀版本。

對長時間執行且有外部副作用的工作，光續接對話還不夠。可恢復的狀態至少要能核對三件事：

  1. 哪些步驟已確認完成，避免重做退款或檔案寫入。
  2. 下一步所需的輸入是什麼，避免只知道進度位置卻無法繼續。
  3. 前面累積的結果及其來源是什麼，避免後續工作依賴憑印象重建的資料。

這些事實應有持久化紀錄；重要階段完成後保存檢查點，恢復時先檢查其完整性，以及所依據的檔案版本、時間或外部狀態是否已變。檢查點粒度有取捨：每步保存可減少重做但增加寫入與狀態管理成本；只在主要階段保存較簡單，卻可能要重做中途的可復原工作。對不可逆的副作用，還要有明確的交易或冪等紀錄，不能僅憑對話中「好像做過」就安全重試。選擇續接、分叉或重開的共同原則，是先確認基線可信，再讓後續行動依新證據前進。
