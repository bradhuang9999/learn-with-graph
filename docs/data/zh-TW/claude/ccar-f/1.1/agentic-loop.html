原始考綱

知識要求

  • 代理迴圈的生命週期：向 Claude 發送請求、檢查 stop_reason（tool_use 或 end_turn）、執行要求的工具，並把結果送回下一輪。
  • 工具結果如何加入對話歷史，使模型能根據結果推理下一個動作。
  • 模型依上下文決定下一個工具，與預先設定的決策樹或工具呼叫順序有何不同。

技能要求

  • 實作代理迴圈的控制流程：stop_reason 為 tool_use 時繼續，為 end_turn 時結束該模型回合。
  • 在輪次之間把工具結果加入對話上下文，讓模型能納入新資訊進行推理。
  • 避免用自然語言訊號判斷迴圈結束、把任意迭代上限當成主要停止機制，或只看 assistant 是否輸出文字就判定完成。

要點筆記

代理迴圈是什麼

代理迴圈(Agentic Loop)讓模型在執行期間根據新觀察決定下一步，而不是由開發者預先寫死每個工具與分支。模型能提出結構化的工具請求；真正執行工具、控制權限、回填結果與強制停止的是執行環境。模型說「我已查詢」不代表外部查詢真的發生。

代理迴圈可用四個環節描述；「選擇／執行／迭代」也可對照成「推理／行動／觀察」：

  1. 感知：讀取目前對話、目標與已回填的工具結果，辨認已知與未知。
  2. 推理與選擇：依新證據決定下一個工具、參數或是否回答；這是模型驅動的部分。
  3. 行動與執行：模型提出結構化工具請求，由有權執行的一方取得成功或失敗結果。
  4. 觀察與迭代：結果加入對話，模型重新感知並調整行動；沒有回填，就沒有根據新觀察重新規劃。

每輪還須驗證工作：把觀察到的結果與目標、預期效果比較。觀察只代表「拿到結果」，不代表「結果達標」；若不符，應根據錯誤或新資訊重規劃，無法安全推進時升級。這個操作節奏也可概括為「蒐集上下文 → 採取行動 → 驗證工作」。

對話與工具結果逐輪累積在上下文視窗，形成暫時的工作記憶；它不是無限容量，也不會自動成為跨工作階段的持久記錄。長迴圈應按任務保留關鍵事實、摘要或修剪不再需要的細節，避免後續回合被過多舊輸出擠滿。

判斷代理與固定工作流程的關鍵是誰在執行時決定下一步。模型即使參與多個節點，只要工具順序和分支由程式預定，仍是工作流程。路徑可預期時，固定流程通常較易測試與稽核；需要隨調查結果改變查找方向時，才值得使用代理迴圈並承擔較高的成本與控制風險。

模型能選工具，是因為工具定義提供名稱、用途描述與參數格式；描述含糊會讓適用時機不明。工具的詳細介面設計留到 2.1，這裡先掌握「模型提出行動，執行方回傳觀察」的邊界。

一次用戶端工具往返的四個步驟

以下是用戶端工具的控制流程：由應用程式自行執行模型請求的工具。伺服器端工具由服務提供方執行，不能把每個工具區塊都當作應用程式要親自呼叫的函式。

  1. 送出目標、可用工具與目前對話，先讀 Claude 回應的 stop_reason，不要先以文字內容猜測是否完成。
  2. stop_reason="tool_use" 時，保留完整 assistant 回應並執行其中每個 tool_use。同一回應可以同時有說明文字和多個工具請求。
  3. 為每個請求產生 tool_result；其 tool_use_id 必須對應原請求的 id。工具失敗也要回傳明確錯誤，不可偽裝為空白成功。把結果作為下一則 user 訊息加入對話，再發出下一輪請求。
  4. stop_reason="end_turn" 只表示模型結束當前回合；執行環境還須檢查業務交付條件。其他停止原因依所用 API 的語意處理，不能一概視為成功。

工具名稱不足以配對結果：同一回應可能兩次呼叫同名工具，只有各自的 ID 能確定哪個結果屬於哪個請求。

例如調查部署異常時，Claude 在同一回應要求 read_log(id=call_a) 與 get_deployment(id=call_b)；即使它同時寫了「我正在核對部署」，stop_reason 仍是 tool_use。日誌查詢成功、部署查詢因權限不足失敗時，執行環境須把兩項結果（含錯誤）各按 ID 配對回填，再讓 Claude 決定下一步；不能只回傳成功的日誌。

停止模型回合，不等於完成任務

任務另有四種停止理由，應分開記錄：

理由 任務狀態與處置
交付條件達成 正常完成，交付已核對的結果。
錯誤達到門檻 失敗或升級，保留已取得證據與錯誤。
時間、費用或回合預算耗盡 安全中止並呈現部分進度；不是成功。
使用者或上層要求停止 受控中止，保存狀態並交還控制權。

回合上限是防失控的保護措施，不是主要完成判準；由執行環境計數並強制中止，不能交給模型自行記數。無限迴圈常見於完成條件不明、工具錯誤無限制重試、或反覆做同一決策卻沒有新觀察。可比較相鄰輪次的工具名稱、參數、結果與未解問題：有新資料、替代方法或可復原錯誤，就可調整路徑繼續；若觸及權限邊界、缺少必要來源或須由人裁決，應停止並升級，不能無方向地重試。

承接上例：即使 Claude 最後以 end_turn 回答「日誌顯示 22:14 起逾時」，應用程式仍須檢查交付條件。部署資料沒有查到，就不能把時間相近的設定變更說成已證實的根因。

三種常見誤判

  1. 以「完成了」等自然語句判定迴圈結束，而不看 stop_reason。
  2. 把任意迭代上限當成「任務已成功」的證據；它只代表預算已用完。
  3. 看到 assistant 有文字就忽略同一回應的 tool_use 區塊。
