原始考綱

**Task Statement 5.3：**在多 Agent 系統中實作錯誤傳播策略。

知識要求

  • 結構化錯誤上下文（失敗類型、已嘗試查詢、部分結果、替代做法）讓協調者能作出明智的復原決策。
  • 存取失敗（如逾時，需要決定是否重試）與有效空結果（查詢成功但沒有符合項目）不同。
  • 「search unavailable」等通用錯誤狀態會隱藏協調者需要的資訊。
  • 悄悄吞掉錯誤、把空結果當成功，與單一失敗就終止整個流程，都是反模式。

技能要求

  • 回傳結構化錯誤上下文，包括失敗類型、嘗試內容、部分結果及可能替代方案，使協調者能復原。
  • 在錯誤回報中區分存取失敗與有效空結果，供協調者作適當判斷。
  • 子代理先在本地復原暫時性失敗；只傳播無法解決的錯誤，並附上已嘗試的方法與部分結果。
  • 綜整輸出應標註涵蓋情況，指出哪些發現證據充足，哪些主題因來源不可得而有缺口。

要點筆記

協調者需要知道子代理取得了什麼、哪些查詢沒有完成，才能決定繼續、換來源或暫停。把逾時包裝成空清單會製造「確定沒有資料」的假陰性；任何小錯都停止整體工作，則會浪費已完成的結果。錯誤傳播的核心是預先定義哪些失敗在本地復原、哪些須跨代理邊界上報，以及上報時帶哪些資訊。

查詢結果的四種互斥狀態

工具包裝器應根據服務回應、逾時與分頁完成情況，對每次指定來源及範圍的查詢產生明確狀態，不能讓代理只從 [] 推測：

狀態 該次查詢實際發生什麼 下游可說什麼
success 已完成，且取得符合資料 可引用已核實結果
success_empty 已完成指定範圍，零筆符合 只能說「在已查範圍未找到」
partial 未完成，但已有可驗證的部分資料 可使用已得資料，必須標示未涵蓋範圍
access_error 未完成且沒有可用資料，例如逾時或權限拒絕 資料是否存在仍未知；不能說「查無」

partial 與 access_error 的界線是該次查詢有沒有可用資料，不只是有沒有逾時。多個查詢組成一個子代理任務時，另設整體覆蓋欄位：甲來源成功、乙來源不可用，乙的狀態仍是 access_error，整個任務的覆蓋則是 partial。單次狀態和整體覆蓋不能混成一個標籤。

在最近的可處理層復原

先判斷失敗層：工具可能因參數或權限被拒，環境可能因網路／資料庫暫時不可用，代理也可能在工具正常時選錯查詢或誤讀結果。補救取決於原因與副作用，而不是只看 HTTP 類別。

  1. 本地復原：查詢逾時、限流等暫時故障可在預設次數與延遲預算內重試；成功後仍記錄異常。參數固定錯誤、權限拒絕或推理選錯路徑，重跑同一呼叫通常無效。
  2. 向協調者傳播：本地重試耗盡、來源不可用、授權／政策阻擋、或失敗會改變上層計畫時，回報具體原因、部分結果及可行下一步。判斷問題是「協調者知道此事後，計畫會改變嗎？」會，就不應默默吞掉。
  3. 協調者選擇：可有限重試、改派代理或查同等權威的來源；可交付已核實的部分結果並標缺口；若缺的是核准退款等高風險決策的必要證據，則停止相依分支並交人工。產品說明頁不會因官方政策庫故障就變成同等政策依據。

有副作用的寫入尤其不能把「請求逾時」當成「沒有執行」。重試退款前先查原操作狀態、已完成步驟與冪等鍵，避免第二次退款。工具回 success: true 但資料庫未更新、分頁漏抓或缺必要欄位，也是無聲失敗；重要階段邊界須驗證回應與外部實際狀態，而非只相信成功碼。

錯誤封裝讓協調者能採取行動

子代理的回報至少帶失敗類型、查詢與範圍、嘗試次數、部分結果、替代途徑、受影響的覆蓋範圍。多步驟或有副作用的任務再帶嚴重度、已完成步驟、操作識別碼／冪等鍵與追蹤識別碼。這是應用層契約，不是指定 SDK 的固定欄位：

overall_coverage: partial
queries:
  - {source: refund_excerpt, status: success, query: 一般退款方式, attempts: 1}
  - {source: official_policy, status: access_error, query: 競品價差例外, attempts: 2, error: timeout}
verified_findings:
  - {claim: 一般退款退回原付款方式, source: refund_excerpt 第2節}
coverage_gap: 競品價差例外未經官方政策庫查證
next_options: [稍後重試, 交人工查證]

此例的官方來源查詢失敗，不是「官方政策沒有例外」。若查詢成功而零筆命中，才改記 success_empty，並附查詢範圍；若逾時前取得一頁有效資料，則記 partial 並列未查頁面。協調者可保留一般退款規則，但不得據此核准競品價差退款。

綜整輸出宜分開標示有來源支持的發現、因來源不可用而有缺口的主題、仍待驗證的推論。警告可記錄後續行，可復原錯誤按預算處理，致命錯誤停止相依分支；嚴重度必須連到具體處理政策。各層使用同一追蹤識別碼並保留工具輸入、輸出和驗證結果，才能從最終錯誤追回最早失真的邊界。
