原始考綱

**Task Statement 2.4：**把 MCP Server 整合進 Claude Code 與 Agent 工作流程。

知識要求

  • MCP Server 的設定範圍：專案層級的 .mcp.json 供團隊共用；使用者層級的 ~/.claude.json 供個人或實驗用途。
  • 在 .mcp.json 展開環境變數（如 ${GITHUB_TOKEN}），可管理憑證而不將祕密提交到版本控制。
  • 連線時會探索所有已設定 MCP Server 的工具，並同時提供給 Agent 使用。
  • MCP 資源可公開內容目錄（如議題摘要、文件階層、資料庫綱要），減少探索性工具呼叫。

技能要求

  • 在專案範圍的 .mcp.json 設定共用 MCP Server，並以環境變數展開驗證權杖。
  • 在使用者範圍的 ~/.claude.json 設定個人或實驗性 MCP Server。
  • 強化 MCP 工具描述，詳細說明能力與輸出，避免 Agent 因資訊不足而偏好內建工具（如 Grep）。
  • 標準整合（如 Jira）優先選既有社群 MCP Server；客製 Server 留給團隊特有流程。
  • 把內容目錄公開為 MCP 資源，讓 Agent 不必先用工具探索就能知道有哪些資料。

要點筆記

先認清 Server、Client 與 Host 的分工

模型上下文協定(Model Context Protocol, MCP)讓應用程式以共同介面連接外部系統，減少每個資料源都要另寫一套整合的負擔。它不是某個搜尋工具：Server 公開能力，Client 建立連線、發現並呼叫能力，Host 把能力接進代理工作階段。在 Claude Code 中，Claude Code 是 Host，替已設定的 Server 維持用戶端連線；模型不能只靠提示詞呼叫尚未連線或未獲准的伺服器。

從連線到結果的路徑

在考綱所用的 MCP 連線模型中，流程是：設定與連線 → 初始化／能力協商 → 列出工具、資源與提示 → 選擇或提供能力 → 呼叫／讀取 → 處理結果。同一工作階段可連多個 Server，由 Client 把工具呼叫送到所屬 Server。工具執行失敗與連線、發現或協定失敗是不同層級；前者可用第 2.2 節的結果契約，後者先查設定、核准、憑證與連線狀態。

Server 公開三種基本能力，判斷法是「誰決定使用它」：

能力 典型控制者 付款調查例子
工具(Tool) 模型按任務呼叫動作或查詢 按議題 ID 查即時狀態。
資源(Resource) Host／應用程式決定讀取 URI 指向的背景資料 提供可用文件或資料表目錄。
提示(Prompt) 使用者選取可重用的起始範本 啟動「付款事件調查」範本。

資源可先公開內容目錄，讓應用程式知道可讀哪些文件，減少盲目試探；目錄可見不等於內容已獲授權。工具適合按需取得最新議題，資源適合呈現背景資料，提示適合由使用者明確發起的流程。

例如團隊自建的議題 Server 可公開一筆 issues://catalog 資源；這是示意 URI，不是 Jira 或 MCP 預設名稱。其內容列出「付款議題摘要 → issues://payment/summary」、「議題欄位說明 → issues://schema」等項目與 URI。Host 先列出資源，再讀取目錄 URI，把可選項及來源交給代理；代理知道有哪些資料後才要求讀取適合的 URI，無須盲試多個搜尋工具。Server 仍須逐筆檢查讀取授權；公開目錄不等於公開所有內容。若 Server 根本沒有提供可列舉清單或目錄資源，就不能假設用戶端會憑空知道這些 URI。

設定作用域與憑證

作用域 設定位置與可見性 選用情境
專案 專案根目錄 .mcp.json，可納入版本控制供團隊共享 所有成員應使用的議題伺服器。
本機 ~/.claude.json 的目前專案項目，只對本人此專案有效 尚未要分享的實驗工具。
使用者 ~/.claude.json，對本人所有專案有效 跨專案常用的個人工具。

考綱以「共享 .mcp.json、個人 ~/.claude.json」對照；實作時還要分清後者的本機範圍與使用者範圍。共享的是連線設定，不是密鑰或自動核准：團隊成員仍須提供自己的憑證，並依 Claude Code 的信任與核准流程啟用專案 Server。Claude Code MCP 設定文件說明現行作用域與環境變數展開。

使用者範圍可在任何專案執行 claude mcp add --transport http personal-issues --scope user https://issues.example.com/mcp；Claude Code 會把它存進本人的 ~/.claude.json，讓本人所有專案可用。本機試驗則改用 --scope local（或省略，因本機是預設）；它也存於 ~/.claude.json，但歸在目前專案路徑之下，其他專案看不到。兩者雖是同一檔案，不能只看檔名判斷作用域；用 claude mcp get personal-issues 核對實際來源與連線狀態。

{
  "mcpServers": {
    "team-issues": {
      "type": "http",
      "url": "https://issues.example.com/mcp",
      "headers": { "Authorization": "Bearer ${ISSUE_TOKEN}" }
    }
  }
}

範例中的 ${ISSUE_TOKEN} 由成員環境提供，不把值寫進版本控制。變數缺失或授權失敗時，應檢查 claude mcp list、claude mcp get 或 /mcp，不可將連線失敗解讀成「議題不存在」。本機程序通常用標準輸入輸出(STDIO)；需跨主機共享的 Server 通常用 Streamable HTTP，並在網路端處理驗證與授權。選傳輸看部署位置，不看能力是工具還是資源。

多伺服器下，先確認「可用」再確認「選對」

「已設定」「已連線」「代理獲准」「模型找得到並選對」是不同條件。多個 Server 可同時提供能力，但 Claude Code 可能按需搜尋並載入 MCP 工具定義，而非每回合把所有描述攤在上下文中。按需載入節省上下文，卻仍依賴清楚的 Server 說明與工具描述；它既不修復模糊邊界，也不取代代理的最小權限。Claude Code MCP 工具搜尋說明提供目前的載入行為。

例如任務要查本週付款議題，遠端 team-issues 工具應寫明它查的是議題庫、可用日期與關鍵字篩選、回傳議題 ID 和更新時間；本機 Grep 則搜尋工作樹內的文字。如果有一份過時議題匯出檔，Grep 命中「付款逾時」也不能證明遠端最新狀態。找不到議題工具時先查連線、核准、能力發現與搜尋說明；找得到卻誤選 Grep，再查描述與資料來源邊界。

標準外部服務可先評估可信、受維護的既有 MCP Server；只有團隊專屬流程、授權或資料契約無法滿足時，才承擔自建成本。任何 Server 都須在執行端驗證參數與權限，不能把工具描述當安全邊界。
