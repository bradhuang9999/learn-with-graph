原始考綱

**Task Statement 3.6：**把 Claude Code 整合進 CI/CD 管線。

知識要求

  • -p（或 --print）旗標可在自動化管線中以非互動模式執行 Claude Code。
  • --output-format json 與 --json-schema CLI 旗標可在 CI 情境強制輸出結構化資料。
  • CLAUDE.md 可為 CI 呼叫的 Claude Code 提供專案上下文，如測試標準、fixture 慣例與審查標準。
  • 工作階段上下文隔離：產生程式碼的同一工作階段通常不如獨立實例有效地審查自身修改。

技能要求

  • 在 CI 中用 -p 執行 Claude Code，避免等待互動輸入而卡住。
  • 合用 --output-format json 與 --json-schema 產生機器可解析的審查發現，供自動發佈為 PR 行內留言。
  • 新提交後重跑審查時提供先前發現，要求只回報新增或仍未修復的問題，避免重複留言。
  • 產生測試時提供既有測試檔作為上下文，避免建議測試套件已涵蓋的重複情境。
  • 在 CLAUDE.md 記錄測試標準、有價值的測試判準及可用 fixture，提高測試產生品質並減少低價值輸出。

要點筆記

CI 中的 Claude Code 是一次性、無人值守的工作步驟。可靠的 PR 審查不能只求一段「看起來合理」的評論；必須分別處理非互動執行、工具與資料權限、可解析結果、評論定位與重跑去重。每層失敗都應被管線辨認，不能被當成「零項發現」。

讓一次審查成為可檢查的管線步驟

層次 機制 必須驗證的事
執行 claude -p／--print 不等待人類輸入；設定逾時，檢查程序退出碼。非互動不代表代理不能多回合讀工具結果。
上下文 版控中的 CLAUDE.md、目前 PR 差異、相關既有測試 測試慣例、fixture、審查準則可被新會話取得；輸入基準版本明確。
權限 限定工具、檔案與憑證 純審查不應有寫入或不必要的網路能力。
輸出 --output-format json 搭配 --json-schema 解析 JSON 包裝，驗證 structured_output.findings 符合業務結構。
發布 PR 評論發布器 確認檔案與行號仍在目前差異中，去除重複評論。

-p 使指令收到提示、執行後輸出並結束；缺少它，互動式工作階段可能在沒有人的 CI 執行器上等待。--output-format json 定義傳輸包裝，--json-schema 定義最終業務資料形狀。下游應讀取 structured_output.findings，而不是把整份輸出或自由文字當成發現清單。Claude Code CLI 旗標文件與結構化輸出文件可核對目前介面。

以下示意在 PowerShell 中把已由 CI 產生、且不含秘密的差異檔送進一次非互動審查；實際管線仍須設定逾時、工具與憑證權限，並檢查退出碼。Schema 是輸出形狀的最小例子，不是「發現真實」的保證：

$reviewSchema = '{"type":"object","properties":{"findings":{"type":"array","items":{"type":"object","properties":{"path":{"type":"string"},"line":{"type":"integer"},"reason":{"type":"string"}},"required":["path","line","reason"]}}},"required":["findings"]}'
Get-Content -LiteralPath 'pr.diff' -Raw | claude -p --output-format json --json-schema $reviewSchema '依 CLAUDE.md 準則審查差異；只回報可定位的功能或安全問題。'

成功執行後先解析外層 JSON，再驗證 structured_output.findings 中每項的路徑、行號和原因；若程序失敗或缺欄位，就停止發布，不可回傳「零項」。此命令示範旗標如何合用，不能取代 CI 對可用工具、檔案及網路的隔離設定。

例如審查結果可要求 findings 為陣列，每項含 path、line、reason；沒有問題時是有效的空陣列。程序非零退出、JSON 無法解析、缺 structured_output、欄位無效或定位已過期，都不是有效的空陣列。Schema 保證形狀，不保證缺陷真實或行號仍對應新提交；發布器仍須自行查核。

若只需讀取程式碼，可用 --tools "Read,Grep,Glob" 限制可用的內建工具；--allowedTools 是免詢問的預先核准，不是白名單；--tools 不限制 MCP 工具，需另用 --disallowedTools "mcp__*" 或適當權限拒絕。若審查需要 Git 差異，管線可先產生差異檔並交給唯讀工作，而非直接授予無範圍的 Bash。執行環境還須限制檔案存取與憑證，提示中的「不要改檔」不是安全閘門。

讓新會話審查已發生的變更

寫碼會話知道原始意圖，容易把「原本打算這樣做」誤當成程式實際行為。獨立審查會話應從目前提交的差異、相依程式、既有測試與共享準則出發；它不會自動知道上一輪討論，因此輸入要自足。CLAUDE.md 應給可操作的團隊規範，例如「先看 tests/fixtures/payments/；只在既有測試未涵蓋可重現行為時建議新測試；發現須附檔案及行號」。測試標準要再具體到：用可重現輸入與可觀察斷言檢查行為、沿用現有 fixture、避免只重測實作細節或改名重複同一情境。不要只存在原作者的個人 CLAUDE.md，否則 CI 新會話拿不到。

在 CI 產生測試時，先查既有覆蓋

產生測試與純審查是不同工作：前者若要寫入測試檔，需在受控工作區授予必要寫入權；後者可保持唯讀。產生測試的呼叫至少取得目前變更、待測函式及相依行為、相關既有測試檔、fixture 位置和上述團隊測試標準。代理先列出既有案例的輸入與斷言，再提出真正未覆蓋的邊界或失敗路徑；若已有同等案例，就回報「無需新增」，不能換個名稱複製一份。

例如付款函式的新變更涉及 amount=500 邊界，而既有測試已涵蓋 499 與 501。有價值的新測試應使用現有付款 fixture，以 500 作輸入，斷言對外可觀察的核准或人工審核結果，並依產品規則確定預期；不要只斷言內部比較運算子。生成後由管線執行新測試及相關回歸測試，檢查測試有實際斷言、能針對目標行為失敗或通過，且沒有與既有案例重複。若規則尚未釐清，應標成待決而非猜一個預期值。

當 PR 新增提交後重新審查，應同時提供目前差異、先前發現、既有測試，要求只回報新問題或仍未解決的舊問題。假設第一次發現「金額可能溢位」和「缺失敗測試」，第二次提交只補了測試：結果應保留溢位、移除已解決測試項。發布器再以穩定的問題識別與目前程式位置去重，避免把同一溢位再貼一次；只靠提示或 --json-schema 都不能保證去重。若行號位移，重新定位或轉人工確認，不應硬貼舊位置。

把 CI 審查視為可重跑的函式：輸入版本和準則清楚、執行可終止、結果可解析、失敗可辨識、重跑不製造重複評論。這些條件比評論文字是否流暢，更能決定它能否安全接到 PR 流程。
