# 3.1 設定 CLAUDE.md 的層級、範圍與模組化

## 原始考綱

**Task Statement 3.1：**依適當的層級、適用範圍與模組化方式設定 `CLAUDE.md`。

### 知識要求

- `CLAUDE.md` 的設定層級：使用者層級（`~/.claude/CLAUDE.md`）、專案層級（`.claude/CLAUDE.md` 或根目錄 `CLAUDE.md`）、目錄層級（子目錄中的 `CLAUDE.md`）。
- 使用者層級設定只對該使用者生效；`~/.claude/CLAUDE.md` 的指令不會透過版本控制分享給隊友。
- `@import` 語法可引用外部檔案，使 `CLAUDE.md` 模組化，例如匯入各套件相關的標準檔。
- `.claude/rules/` 可按主題組織規則檔，取代單一龐大的 `CLAUDE.md`。

### 技能要求

- 診斷設定層級問題，例如新隊友收不到指令，是因為指令放在使用者層級，而不是專案層級。
- 依維護者對領域的了解，在各套件的 `CLAUDE.md` 用 `@import` 選擇性納入相關標準。
- 把大型 `CLAUDE.md` 拆成 `.claude/rules/` 中聚焦主題的檔案，例如 `testing.md`、`api-conventions.md`、`deployment.md`。
- 用 `/memory` 指令確認載入了哪些記憶檔，診斷不同工作階段的行為不一致。

## 要點筆記

### 先分清作用域、載入時機與是否遵循

`CLAUDE.md` 是提供 Claude Code 的專案脈絡與工作指示，不是權限或安全沙箱。配置它有三個不同問題：**規則放在哪個作用域、何時載入、如何驗證確實生效**。團隊規則若只寫在個人檔案，其他人 clone 專案後不會取得；規則被載入，也不代表一定被遵循。

### 用受眾與工作範圍決定位置

1. 使用者層 `~/.claude/CLAUDE.md`：只屬於該使用者，跨其專案使用，例如個人回覆偏好；不會因提交儲存庫而分享給隊友。
2. 專案層根目錄 `CLAUDE.md` 或 `.claude/CLAUDE.md`：供整個團隊使用，應納入版控，例如架構邊界、標準測試命令。兩者是專案指示的可選位置，無須複製同一規則到兩處。
3. 目錄層 `packages/api/CLAUDE.md`：放該目錄的專屬慣例；在 Claude 讀取其下檔案時按需載入。跨多個目錄的同類檔案，則考慮 3.3 的路徑規則。

現行文件另有組織管理層與本機 `CLAUDE.local.md`。考綱重點是前三種範圍；前者用於全組織管理，後者適合不分享的單專案偏好。`CLAUDE.md` 是寫給模型的上下文，**不是強制執行的權限規則**。衝突指示可能讓模型任選其一：載入順序由廣到窄，不代表「最近的檔案必定勝出」。實務上應移除衝突，必要的硬限制交給權限設定或工具前攔截。

三層的差別是**誰能取得指示、何時會接觸指示**。遇到行為不一致，先查可見性與載入條件，再查規則文字。

### 規則要寫到能執行，也能檢查

位置正確不代表內容有用。若根檔只寫「寫出高品質程式碼，記得測試」，Claude 仍得猜使用哪個測試命令、何時必跑、失敗怎麼處理。有效的 `CLAUDE.md` 應記錄**這個儲存庫特有、模型不可能自行可靠推知**的決策：適用範圍、可執行動作與可檢查的結果。例如在 API 套件規則中寫：

```markdown
# API 套件變更
- 修改 `packages/api/src/` 後，執行 `pnpm --filter api test:contract`。
- 若契約測試失敗，回報失敗測試名稱與輸出；不得宣稱驗證完成。
- 新端點的錯誤回應沿用 `packages/api/src/errors.ts` 的格式。
```

這三行分別給出觸發條件、驗證命令、失敗處置與既有契約位置；讀者與代理都能查它是否被遵循。相反，「遵守最佳實務」無法驗證；把 Python 語法教學或格式化工具已強制的每條排版規則再抄進來，只會佔用上下文並建立第二個可能過時的真實來源。根檔只保留整庫通用的入口、測試與安全邊界；API、前端、基礎架構各自的命令與慣例放在其目錄檔或帶路徑條件的規則。跨套件共用的型別或匯入限制，則在共用專案規則明確指向所有受影響套件，避免每份局部檔各寫一版、日後互相衝突。

若這個 API 契約測試命令只在個人層，隊友讀不到；若放根檔，前端工作又會讀到無關指示。應把它放在共享且適用的範圍，用實際 API 變更測試載入與遵循。硬性的禁止寫入或秘密存取仍須權限拒絕或執行環境隔離。

### 兩種模組化方法

當一個檔案混有前端、API、部署三套長篇規則，會增加不相關上下文，也使維護者難找規則。可依用途選擇：

| 方法 | 適合情況 | 載入與成本 |
|---|---|---|
| `@import` | 套件維護者已知應引用哪份標準，要在該套件 `CLAUDE.md` 明確組裝 | 例如 `@../../docs/api-standards.md`；相對路徑以**包含匯入語句的檔案**為基準。匯入內容仍進入上下文，不是省 token 的開關 |
| `.claude/rules/` | 大型專案按主題維護 `testing.md`、`api-conventions.md`、`deployment.md` | 無 `paths` 的規則一般載入；有 `paths` 的規則對匹配檔案按需套用，細節見 3.3 |

`@import` 可引用外部檔案；現行文件指出專案指示首次引用工作目錄外檔案時可能需核准。團隊共享範例宜先用儲存庫內路徑，避免新同事的環境指向不存在的個人檔案。

`@import` 是在一份指示檔中**明確選入**；`.claude/rules/` 是集中維護，配合 `paths` 可依路徑**條件選入**。若規則都無條件載入，拆檔不會減少無關上下文。

### 範例：新同事收不到 API 規則

維護者在個人 `~/.claude/CLAUDE.md` 寫「API 變更須執行契約測試」，隊友 clone 後卻讀不到。這是團隊規範，應移到版控中的專案檔；若細節只屬於 API，可放 `packages/api/CLAUDE.md`，必要時以 `@../../docs/api-standards.md` 組裝共用標準。若同類 API 規則散在多處，則集中到帶路徑條件的 `.claude/rules/`。兩種做法擇其適用者，不需同時複製同一條規則。

驗證分兩步：用 `/memory` 查看記憶檔位置、開啟檔案以排查放錯層級；在**目前會話**用 `/context` 的 Memory files 清單確認實際載入。考綱把 `/memory` 寫成驗證載入的入口；現行產品文件已把直接確認載入清單的做法寫成 `/context`。載入後仍應用一個具體任務檢查規則是否被遵循，因載入不等於強制執行。

不要只在原維護者機器上驗證，因個人檔案仍可能生效。應用沒有該個人規則的新會話或隊友環境，依序確認版控檔案存在、`/context` 顯示已載入、實際 API 變更有執行契約測試。前兩步查配置，最後一步查行為。
