# 3.2 建立並設定自訂斜線指令與技能

## 原始考綱

**Task Statement 3.2：**建立並設定自訂斜線指令與技能。

### 知識要求

- 專案範圍的指令存於 `.claude/commands/`，可經版本控制共享；使用者範圍的指令存於 `~/.claude/commands/`，供個人使用。
- `.claude/skills/` 中的技能以 `SKILL.md` 定義，其 frontmatter 可設定 `context: fork`、`allowed-tools`、`argument-hint`。
- `context: fork` 可讓技能在隔離的子代理上下文執行，避免技能輸出污染主對話。
- 可在 `~/.claude/skills/` 建立不同名稱的個人技能變體，避免影響隊友。

### 技能要求

- 在 `.claude/commands/` 建立專案範圍斜線指令，透過版本控制供全團隊使用。
- 對產生大量輸出（如程式庫分析）或探索性上下文（如方案發想）的技能使用 `context: fork`，使其與主工作階段隔離。
- 在技能 frontmatter 設定 `allowed-tools` 以限制執行時的工具存取，例如只允許檔案寫入、避免破壞性動作。
- 在技能 frontmatter 設定 `argument-hint`，提示未提供參數的開發者補上必要資訊。
- 區分適用於特定任務、按需呼叫的技能，與始終載入、適用全局標準的 `CLAUDE.md`。

## 要點筆記

### 先區分常駐規範與按需任務

`CLAUDE.md` 保存持續適用的專案脈絡；自訂斜線指令與技能保存**按需使用的任務或參考流程**。例如「API 變更須執行契約測試」是規範，「審查這次 API 差異並回報缺陷」是可呼叫的工作。把後者整段塞進常駐檔，平日也要負擔其上下文；把前者只放技能，未啟動技能時又可能漏掉。

### 選擇入口與分享範圍

| 載體 | 位置與使用方式 | 適用情況 |
|---|---|---|
| 專案自訂指令 | `.claude/commands/review-api.md`；檔名成為 `/review-api`，可隨版控分享 | 簡短、單一任務的團隊入口。 |
| 個人自訂指令 | `~/.claude/commands/`，不隨專案分享 | 個人快捷流程。 |
| 專案技能 | `.claude/skills/review-api/SKILL.md`，可附參考檔與腳本 | 需多檔資源、描述匹配或較豐富執行設定的重複工作。 |
| 個人技能 | `~/.claude/skills/<不同名稱>/SKILL.md` | 個人變體；避免改動或遮蔽團隊共享版本。 |

現行 Claude Code 將自訂指令納入技能機制，舊 `.claude/commands/` 仍可使用；選擇重點是流程複雜度、如何啟動，以及誰需要取得它。[Claude Code 技能文件](https://code.claude.com/docs/en/skills)列出目前的行為。技能的 `description` 說明適用任務，會影響 Claude 是否在相關請求下選用；若只寫「協助開發」，便無法與其他技能區分。可直接呼叫的名稱宜用動作與對象，例如 `/review-api`，而非 `/do-everything`。

### 把任務寫成可重複執行的契約

一項指令只處理一個有明確產物的工作。正文至少交代四件事：**處理觀點、確切任務、回傳格式、範圍限制**。此外要說清輸入從何而來；「審查本次差異」若沒有基準版本或差異檔，就不是可執行的指示。多個輸入應明定缺值與錯誤路徑，不能任意挑檔代替。

例如唯讀 API 審查可要求套件路徑與 CI 已產生的差異檔：先確認兩者存在、差異限於該套件，再讀相關程式及測試，只回報可定位的行為缺陷。審查、修復和部署不應藏在同一入口；前一項產物可供後一項使用，但是否進入下一階段應明確決定。技能正文也不必複製整份 `CLAUDE.md`，否則團隊規則更新後容易出現兩份互相矛盾的版本。

### 三個 frontmatter 欄位分別控制什麼

| 欄位 | 效果 | 不能誤認為 |
|---|---|---|
| `context: fork` | 用獨立子代理執行技能，讓大量探索內容留在隔離上下文，主會話收結果 | 子代理會繼承先前完整對話；技能必須自含任務與輸入。 |
| `allowed-tools: Read Grep Glob` | 在呼叫該技能的回合預先核准列出的工具 | 工具白名單；未列工具仍依一般權限規則處理。 |
| `argument-hint: "[package] [diff-file]"` | 在呼叫入口提示使用者應輸入什麼 | 自動驗證參數；正文仍須檢查缺值與路徑。 |

考綱將 `allowed-tools` 說成限制工具，但[現行官方文件](https://code.claude.com/docs/en/skills)明確說它是**預先核准**，不會移除其他工具。若必須封鎖寫入，要用 `disallowed-tools`、權限拒絕規則或執行環境限制；「不得修改」的正文只是行為指示，不是安全閘門。

```yaml
---
name: review-api
description: 唯讀審查指定 API 套件的變更與既有契約測試，回傳可定位的缺陷
argument-hint: "[package] [diff-file]"
context: fork
allowed-tools: Read Grep Glob
disallowed-tools: Edit Write Bash
---
將 $ARGUMENTS 解析為套件路徑與差異檔；缺值或路徑不存在就先停止並索取。
確認差異落在指定套件，讀取相關原始檔與測試。
只回報本次變更造成的缺陷，附檔案位置、重現條件與理由；不得修改或發布。
```

此範例假設差異檔已由外部流程提供；若未提供，技能在上述工具範圍內不能自行產生它。`context: fork` 適合搜尋數百個呼叫點、主會話只需審查結論的任務；回來的是摘要，不是完整搜尋歷史。若下一步要改程式，主會話仍須重新核對關鍵檔案。若工作高度依賴剛才對話中的未寫明決定，先補齊輸入或留在主會話執行，不應以分叉期待自動繼承。
