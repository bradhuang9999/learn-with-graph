# 3.4 判斷計畫模式與直接執行的使用時機

## 原始考綱

**Task Statement 3.4：**判斷何時使用計畫模式，何時直接執行。

### 知識要求

- 計畫模式適用於大型變更、多種合理方案、架構決策及跨檔修改等複雜工作。
- 直接執行適用於簡單、範圍明確的變更，例如在單一函式增加一項驗證。
- 計畫模式讓代理在提交修改前安全探索程式庫並設計方案，避免昂貴的返工。
- `Explore` 子代理可隔離大量探索輸出，只把摘要送回主對話，以保留主上下文。

### 技能要求

- 對有架構影響的工作選計畫模式，例如微服務重組、影響 45 個以上檔案的函式庫遷移，或基礎設施需求不同的整合方案選擇。
- 對範圍清楚且已理解的變更直接執行，例如堆疊追蹤清楚的單檔錯誤修正，或增加日期驗證條件。
- 大量探索時使用 `Explore` 子代理，避免多階段工作耗盡主上下文視窗。
- 先用計畫模式調查，再直接執行已定方案，例如先規劃函式庫遷移、後落實遷移。

## 要點筆記

### 選模式看未知決策與返工代價

計畫模式(Plan Mode)把**探索與設計**放在寫入之前：先讀程式碼、釐清方案與風險，再由人審核，之後才執行。直接執行則在需求、影響範圍與驗證方式已清楚時省去正式提案。選擇取決於尚未解決的決策與犯錯代價，不取決於「所有改程式都先寫計畫」的儀式。

### 四個判斷問題

1. **範圍已知嗎？**單一函式且堆疊追蹤明確，可讀取、修正並測試；跨多模組的呼叫點未查清，先探索。
2. **有多個合理方案嗎？**若整合方式牽涉不同基礎設施、資料遷移或對外介面，先比較取捨。
3. **錯誤是否難回退？**大範圍遷移或契約變更須先定不變條件、分批驗證和回退路徑。
4. **探索資料會淹沒主會話嗎？**大量讀檔與搜尋可交 Explore 子代理，要求回報呼叫點、證據路徑和未確認事項；主會話仍須核對關鍵證據。

因此 `validateDate("")` 的單檔修正若已有失敗測試，通常直接改、跑測試即可。把 45 個檔案中的驗證函式庫換掉，且 API 與批次任務錯誤格式不同，則要先查相依、比較遷移順序與回退方式。計畫模式處理**未知決策**；Explore 子代理處理**大量發現的上下文成本**，兩者可搭配，但不是同一機制。簡單兩檔探索直接在主會話看，反而較好核對。

### 計畫的核准閘門要檢查什麼

一份可供執行的計畫須寫出預計變更的模組或檔案、步驟順序、維持不變的對外契約、測試與回退方式，以及尚未確認的假設。審核者至少查三件事：

1. **意圖與範圍**：原本只要換驗證函式庫，計畫卻順手重寫付款流程，就應刪減範圍。
2. **路徑與相依**：預計修改的檔案是否存在、包裝層與呼叫端是否都列入？若摘要標示某呼叫端未追到，不能宣稱影響範圍已確定。
3. **風險與驗收**：每一批如何證明錯誤格式未變？若失敗，如何停止或回退？

人可核准、修改後核准或拒絕計畫；核准只是允許進入執行的檢查點，**不是計畫從此必然正確的證明**。計畫模式的前置成本適合不確定性高的工作，對明確小修正則可能拖慢回饋。

### 假設失效時的處理

執行中若發現匯出名稱不同、預期檔案不存在，或某呼叫端依賴舊錯誤格式，先指出**哪項假設失效、哪些後續步驟受影響**。只影響一個局部步驟時，修訂該步並重跑相關測試；若多個階段都依賴它，暫停擴大寫入、重新探索並修訂計畫，再請審核者確認新範圍。最危險的是默默加入未核准的步驟，最後交付的變更已不是原先審過的方案。

直接執行也可提升為計畫任務：若 `validateDate` 修正途中發現空字串被多個模組當作「未指定」，問題已變成相容性決策，應停下來重新界定，而不是為維持原模式繼續猜。模式是可切換的風險控制，不是任務一開始選了就不能變。
