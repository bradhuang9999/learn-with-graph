# 2.1 設計描述清晰且邊界明確的工具介面

## 原始考綱

### 知識要求

- 工具描述是大型語言模型選擇工具的主要依據；描述過短會讓相似工具之間的選擇不可靠。
- 工具描述應包含輸入格式、查詢範例、邊界情況及使用範圍說明。
- 描述模糊或重疊會造成錯誤路由，例如 `analyze_content` 與 `analyze_document` 的描述幾乎相同。
- 系統提示的措辭也會影響工具選擇：依關鍵字觸發的指令可能造成非預期的工具聯想。

### 技能要求

- 撰寫能區分各工具用途、預期輸入與輸出，以及何時應選它而非相似工具的描述。
- 重新命名並更新工具描述以消除功能重疊，例如把 `analyze_content` 改成具有網頁專屬描述的 `extract_web_results`。
- 把通用工具拆成輸入／輸出契約明確的專用工具，例如將 `analyze_document` 拆成 `extract_data_points`、`summarize_content`、`verify_claim_against_source`。
- 檢查系統提示是否含有依關鍵字觸發、可能蓋過良好工具描述的指令。

## 要點筆記

### 選對工具、組對引數、通過驗證是三回事

工具介面是代理與外部能力之間的契約。要讓一次工具呼叫可靠，必須分清三道關卡：**工具描述幫模型選對工具，輸入結構描述幫模型組成引數，後端驗證確認資料與權限真的有效**。通過前一道關卡，不代表後一道也已通過。

| 關卡 | 要回答的問題 | 典型失敗 |
|---|---|---|
| 工具描述(Tool Description) | 這項任務該用哪個工具？ | 兩個工具都寫「分析內容」，模型誤選資料源。 |
| 輸入結構描述(Input Schema) | 呼叫要帶哪些欄位、型別與允許值？ | 選對查詢工具，卻把姓名填進 `customer_id`。 |
| 後端驗證 | 值是否存在、呼叫者是否有權使用、是否符合業務規則？ | ID 格式正確，卻指向未授權的客戶。 |

### 讓工具描述成為路由依據

工具路由(Routing)是模型依目前請求，從可用工具中選擇合適能力。名稱可以提示用途，但主要的語意依據是描述；名稱、結構描述與系統提示也可能影響選擇。僅把 `analyze_content` 改成 `web_analyzer`，不能補足「讀取網頁」與「判斷主張」的責任差異。

**三段式路由骨架**是「做什麼、何時使用、何時不要使用」；撰寫工具介面時還須補足輸入與輸出契約。逐項檢查如下：

1. **做什麼、何時用**：說明資料來源、具體動作與觸發情境，而非只寫「處理內容」。
2. **收什麼**：指出識別碼或網址等輸入格式，必要時附一個典型請求；範例用來消歧，不替代結構描述。
3. **回什麼**：說明是主文、來源位置、狀態或其他結果，讓模型知道它能否完成當前任務。
4. **不做什麼**：寫明相鄰工具應承擔的工作及存取限制。例如「擷取公開網頁主文；不讀本機 PDF，也不查證主張真偽」。負面邊界能打破相似工具之間的平手。

描述缺少觸發條件，容易讓模型找不到合適工具；缺少排除邊界，容易讓兩個工具都像合適候選；缺少輸出說明，則可能選到無法提供所需證據的工具。這些是介面設計問題，不宜先用更強硬的「看到某個關鍵字就呼叫某工具」系統提示掩蓋。

路由失敗先辨認是哪一種：**沒有適合工具**時，應釐清請求或補上真正缺少的能力，不能硬選「最接近」的工具；**兩個工具都像合適**時，先用資料來源、動作與負面邊界消歧，再考慮調整系統提示。只改名稱、加更多同義關鍵字或新增第三個泛用工具，通常不會解決重疊。

### 把輸入契約寫到可執行

描述解決選擇，輸入結構描述則宣告欄位名稱、型別、必要性與限制。參數名稱應表達領域意義：`customer_id` 比 `data` 清楚；欄位描述還應交代值的來源與格式。只有 `type: string`，無法區分已驗證客戶 ID、姓名與電子郵件。

- **必要與選用**：沒有值就無法執行，才列入 `required`。能以安全預設值運作的欄位可設為選用，並由實作明確處理缺值；若必填值尚不存在，應先取得或詢問，不能編造一個來滿足結構。
- **固定值與其他限制**：少量、穩定的選項用 `enum`；日期格式、字串模式、長度與數值範圍用適用的限制表達。嚴格工具輸入約束可以限制受支援的引數形狀，但各項限制的強制程度取決於介面與模式；不能把所有宣告都當成業務保證。
- **後端責任**：即使引數符合結構，仍需檢查格式、範圍、資源存在性、授權與業務條件。描述中的「只讀公開資料」也不是存取控制，權限必須由執行端落實。

例如查詢工具需要 `customer_id`，但 `from_date` 只是篩選條件，便可把後者設為選用並定義預設查詢範圍。模型若沒有可信的客戶 ID，正確動作是先查詢或請使用者補充；嚴格模式只能約束形狀，無法證明 ID 是真的。結構化輸出與 `strict` 的較完整用法見第 4.3 節。

### 用一個重疊案例檢驗整套介面

使用者說：「取出這個網址中的三項統計數字，稍後逐項核對原文。」若 `analyze_content` 和 `analyze_document` 都描述為「分析內容並回傳摘要」，模型可能把網址交給文件工具，得到沒有原文位置的摘要；後續查證便失去依據。應先辨認重疊的是**描述**還是**實際能力**：

1. 若現有工具本來就只讀網頁，將它改名為 `extract_web_results`，並寫明網址輸入、回傳主文與來源位置、不讀本機文件，也不判斷真偽。同步更新相鄰文件工具的排除條件。
2. 若一個泛用工具混合了不同輸入與結果契約，才考慮拆成 `extract_data_points`（事實點與來源位置）、`summarize_content`（濃縮已取得內容）及 `verify_claim_against_source`（逐項判斷主張與證據）。拆分不是越細越好：若動作共享同一契約，明確的 `action` 參數也可能比增加工具更容易選擇。
3. 檢查系統提示是否仍寫著「凡遇到『分析』一律用 `analyze_document`」。這類關鍵字規則會與新描述衝突；改以資料型態、任務階段與例外條件指路。

若採取第二種做法，三個工具至少要有可區分的契約；它們不是每次都必須依序呼叫的固定管線：

| 工具 | 何時用、收什麼 | 回什麼、不做什麼 |
|---|---|---|
| `extract_data_points` | 已有含來源位置的網頁或文件內容，要抽出指定數值；輸入為內容、來源識別與欲擷取欄位。 | 回傳數值、單位及原文位置；找不到就明示缺值，不自行補數字或判斷真偽。 |
| `summarize_content` | 已取得內容，需要濃縮主要論點；輸入為內容與摘要目的。 | 回傳摘要及涵蓋範圍；不把摘要當逐項引用證據，也不擷取尚未取得的網頁。 |
| `verify_claim_against_source` | 已有待核對主張與可定位的來源原文；輸入為主張、來源識別和原文位置。 | 回傳支持／反駁／證據不足及所據原文位置；來源無法讀取時回報失敗，不捏造查證結論。 |

在本例，先用網頁工具取得附網址與段落位置的內容，再由 `extract_data_points` 抽三項數字；等使用者提出要核對的具體主張，才用 `verify_claim_against_source`。若只是要概覽頁面才選 `summarize_content`，不能讓摘要取代數值與原文位置。

例如，`extract_web_results` 的描述可以寫成：「使用者提供公開網址、需要擷取可追溯的網頁內容時使用，例如『讀取這頁並列出三項數字及所在段落』。輸入為網址；回傳主文、標題、來源網址與段落位置。無法存取時回傳失敗，不以空白主文代替。不讀本機文件，也不判斷數字是否屬實。」這比「分析內容」同時交代了觸發、輸入、結果、邊界與例外。

### 驗證路由是否真的穩定

部署前至少測三類請求：**正例**確認選對工具與引數；**反例**確認不把工具用到界外；**曖昧例**確認相鄰工具有可說明的分界。對同一意圖換幾種措辭，並檢查「沒有適合工具」時是否釐清，而非硬選一個錯得最少的工具。上線後記錄請求與所選工具，觀察新增工具或改寫描述是否造成路由漂移；若已有能力足以處理新請求，先修描述，再考慮加工具。

**判斷題：**若 `search_records` 與 `search_web` 都只寫「搜尋並回傳結果」，把前者改名為 `customer_search` 就足夠嗎？**不夠。**還需明確寫出內部紀錄的資料來源、輸入與回傳內容，以及「不搜尋公開網頁」的邊界，並用正例、反例和曖昧例驗證。
