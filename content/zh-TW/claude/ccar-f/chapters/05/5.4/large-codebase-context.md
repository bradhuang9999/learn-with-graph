# 5.4 在大型程式庫探索中管理 Context

## 原始考綱

**Task Statement 5.4：**在大型程式庫探索中有效管理上下文。

### 知識要求

- 長時間工作階段中的上下文退化：模型開始給出不一致答案，或引用「典型模式」，而不是先前實際找到的類別。
- 暫存筆記檔可跨上下文邊界保存關鍵發現。
- 委派子代理可隔離大量探索輸出，讓主代理維持高層協調。
- 結構化狀態持久化可支援當機復原：各代理把狀態匯出到已知位置，協調者續接時載入 manifest。

### 技能要求

- 建立子代理調查具體問題（如「找出所有測試檔」「追蹤退款流程依賴」），主代理保留高層協調。
- 讓代理維護記錄關鍵發現的暫存筆記，後續提問時重新參照，以抵抗上下文退化。
- 完成一階段探索後先摘要關鍵發現，再建立下一波子代理，並將摘要注入其初始上下文。
- 設計當機復原：代理匯出結構化狀態，協調者續接時載入 manifest 並放入代理提示。
- 長時間探索時，若上下文被大量發現輸出填滿，使用 `/compact` 降低上下文用量。

## 要點筆記

大型程式庫探索會產生許多搜尋命中、候選檔案與錯誤方向。它們佔滿主代理上下文後，模型可能不再引用先前實際找到的類別，反而用「典型系統通常如此」猜測。解法不是保留全部搜尋輸出，而是讓**可驗證發現留得住、雜亂的中間內容留在局部**。

### 兩種狀態檔，保存不同尺度

| 狀態 | 誰使用 | 至少記什麼 |
| --- | --- | --- |
| 工作筆記(scratchpad) | 一條調查線與接續該線的代理 | 已驗證結論、檔案與行號、觀察的程式庫版本、排除過的方向、未解問題、下一個查詢；待驗證線索與事實分開 |
| 恢復清單(manifest) | 協調者 | 各調查線的擁有者、狀態檔位置、最後已驗證檢查點、完成狀態、相依關係與程式庫版本 |

工作筆記回答「這條線查到了什麼、下一步做什麼」；manifest 回答「有哪些線、誰做完、當機後該載入哪份檔案」。兩者都不應複製整段程式碼作為第二個權威來源。程式碼以目前版本的原始檔為準，筆記只留定位與結論。

### 何時委派探索

跨多個候選檔案、需多輪搜尋的調查，適合交給子代理在自己的上下文中吸收冗長輸出，只向主代理回傳短發現；已知路徑的單一短檔案直接讀取較省協調成本。每份委派提示明定四個邊界：**單一問題、搜尋範圍、回傳契約、停止條件**。例如查 `RefundService.submit` 的權限檢查，要求最多三個來源路徑與行號、各一行依據、未查分支，查完入口或到達搜尋預算即停止。探索型代理只給必要的讀取／搜尋工具，不附帶修改或部署權限。

第一輪結束後，協調者先把核實的結論濃縮成下一輪的共同基線，再派 B、C 分查支付回呼與授權；兩者不必各自重讀 A 的所有搜尋輸出。子代理回報是**待核對的跨邊界資訊**：若要據此改權限或宣稱漏洞不存在，主代理須重讀關鍵檔案、核對版本與測試；子代理未查的範圍不能被改寫成「不存在」。

### 中斷時如何恢復

假設 A 已核實退款入口，B 正追支付回呼，C 的授權搜尋只有兩個尚未驗證的候選。A、B、C 各寫自己的工作筆記，協調者寫 manifest；一筆最小的 manifest 紀錄可為：

```yaml
repository_revision: abc123
investigations:
  - {topic: refund-entry, state_file: state/refund.md, status: done, checkpoint: verified-submit, observed_revision: abc123}
  - {topic: payment-callback, state_file: state/payment.md, status: in_progress, checkpoint: verified-callback-entry, observed_revision: abc123, depends_on: refund-entry}
  - {topic: authorization, state_file: state/auth.md, status: in_progress, checkpoint: verified-search-scope, observed_revision: abc123, depends_on: refund-entry}
```

恢復時按順序：**讀 manifest → 比對程式庫版本與證據檔 → 載入各工作筆記 → 重查已失效證據 → 只重派未完成工作**。若 A 的入口因程式碼變更而失效，依賴它的 B、C 結論也要重審。檢查點必須指向*已驗證*進度；「搜到兩個候選」不能寫成「授權邏輯已確認」。格式與檔案路徑由實作團隊定義，Claude Code 不會自動建立上述 manifest。

### 壓縮與維護的邊界

Claude Code 長會話可用 `/compact` 降低上下文佔用，但壓縮前先把不可遺失的路徑、決策與下一步寫到工作筆記；壓縮後重讀筆記和 manifest。壓縮只解決**目前會話的容量**，不能取代跨當機狀態檔，也不保證舊程式碼逐字保留。關鍵檔案變更後要重讀原文。

工作筆記每輪更新目前狀態，刪除已解決待辦與過時猜測，保留反證和必要來源定位；過時筆記比沒有筆記更容易誤導。共用檔案須有擁有者，避免多代理覆寫；憑證、私人資料和大段原始搜尋輸出不要寫入可提交的筆記。若證據需要逐字稽核，另存受控位置並在筆記留下索引。

**恢復檢查**：manifest 指向三份狀態檔，但程式庫版本已變，可以直接合併嗎？不能；先找出版本變更影響的證據檔與相依調查，重驗後再把仍有效的基線注入新一輪探索。
