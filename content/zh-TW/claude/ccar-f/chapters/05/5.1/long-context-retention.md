# 5.1 在長互動中保留關鍵對話資訊

## 原始考綱

**Task Statement 5.1：**管理對話上下文，在長時間互動中保留關鍵資訊。

### 知識要求

- 漸進式摘要的風險：把數值、百分比、日期及客戶明確表達的期待，壓縮成模糊敘述。
- 「中段資訊遺失」效應：模型對長輸入開頭與結尾處理較可靠，卻可能漏掉中段的發現。
- 工具結果會逐漸累積於上下文，耗用的 token 可能遠高於其相關性，例如訂單查詢回傳 40 多個欄位，實際只需 5 個。
- 後續 API 請求須帶入完整對話歷史，以維持對話連貫性。

### 技能要求

- 把交易事實（金額、日期、訂單號碼、狀態）萃取到持久化的「案件事實」區塊，每次提示都帶入，且與已摘要的歷史分開。
- 多問題工作階段另設上下文層，擷取並保留結構化議題資料（訂單 ID、金額、狀態）。
- 工具輸出累積進上下文前，只保留相關欄位，例如訂單查詢中與退貨有關的資料。
- 聚合輸入的開頭放關鍵發現摘要，詳細結果加上明確章節標題，以減輕位置效應。
- 要求子代理在結構化輸出中附上日期、來源位置與方法背景，支援下游正確綜整。
- 下游代理上下文預算有限時，調整上游代理輸出結構化資料（關鍵事實、引文、相關性分數），而非冗長內容與推理鏈。

## 要點筆記

長對話的難題不只是「上下文裝不下」，而是壓縮後仍須找得到**精確事實**。上下文視窗(Context Window)是模型在一次請求中可讀取的內容，包括指示、對話歷史、工具結果與注入資料；不在這次輸入裡、也沒有經工具讀回的舊資訊，模型無法憑空記得。應用程式使用無狀態的 Messages API 進行多輪對話時，須在後續請求重新提供對話歷史；當歷史過長，才有意識地以摘要、案件事實與近期原話取代較舊部分，不能假設服務端自動保留前文。

### 先區分三層資訊

| 層次 | 保存什麼 | 不能代替什麼 |
| --- | --- | --- |
| **案件事實區** | 訂單號、金額、日期、狀態、顧客明說的期待，以及來源、核對時間 | 不能把未核實的說法當成交易紀錄；必要時須回查原始來源 |
| **問題狀態層** | 各訴求的已查結果、未決問題、下一步和負責方 | 不能把多張訂單混成一個籠統的「退款問題」 |
| **滾動對話摘要** | 對話目標、決策理由與近期脈絡；壓縮寒暄、重複推理 | 不能作為精確值或識別碼的唯一帳本 |

摘要保留敘事，未必保留原值：「訂單 A-71 付款 NT$2,480，顧客希望週五前退回原卡」可能只剩「顧客詢問退款」。尤其反覆摘要上一次摘要時，識別碼、數值限制、具名實體與已作決策會逐輪淡化，表現為忘記約束、弄混實體或重開已定案的選擇。摘要讀起來流暢，不代表其中的數字可用；缺值必須標示未知或回查，不能猜補。

這三層說明資訊各放在哪裡；要讓案件事實區可靠，還須建立以下五個擷取、更新與取用環節。

#### 案件事實區的五個運作環節

1. **先擷取**：在摘要原始回合或工具結果之前，依明確類別擷取識別碼、數值、日期、狀態、顧客期待及決策；沒有資料的欄位標成未知，不能自行補齊。
2. **更新並驗證**：把新值與現有值比對，記錄來源及時間，檢查型別、範圍和原話是否一致。更正是否覆蓋舊值，取決於值的歷史是否重要：要保留變更脈絡時追加紀錄，只需目前值時可取代，但重大衝突不可靜默覆寫。
3. **注入當次請求**：按案件和本輪任務取出相關事實，放入與敘事摘要可區分的明確區段；資料只存在資料庫裡而未注入，模型仍看不到。
4. **管理容量與時效**：設定事實區預算，合併重複項、區分長期與暫時事實，按政策淘汰或移出過期資訊；可回查來源不可因裁切而失去唯一副本。
5. **要求模型查閱**：明示答覆前須核對事實區，遇到 `null`、過期資料或互相矛盾的值應查證或說明不確定。僅建立區塊而沒有使用指示，不能保證它會影響回答。

順序的關鍵是**擷取與驗證在壓縮之前**。先把原話壓成「一筆退款」，再想從摘要找回 NT$2,480，已經太晚。若長會話逐漸偏離原目標，可重新開始工作階段，只帶入仍有效的決策、已核實事實與必要近期回合；這是重建上下文，不是清空案件狀態。

### 上下文內資訊與跨會話記憶

上下文內記憶只是「資訊仍在目前請求裡」；摘要捨棄或重開會話後，它可能消失。跨會話持久性則依賴應用程式控制的外部儲存與記憶工具：模型提出讀寫請求，應用程式執行並回傳結果，模型不直接擁有永久記憶。新的工作階段先按案件識別碼讀回、核對權限與資料時間，再將必要內容注入本次請求；進行中的重要進度應持續寫入，不要等結束前才保存。**摘要處理容量，外部記憶處理持久性，案件事實區處理當次精確取用**，三者分工而非互相替代。

### 工具輸出與多代理交接：讓訊號進入上下文

工具結果會佔用後續請求的詞元預算。若查詢回傳 43 欄、退款判斷只需 5 欄，應在**工具回應進入模型上下文之前**的包裝層處理；只精簡人類畫面而仍把 43 欄交給模型，沒有減少上下文壓力。可依資料特性選擇：

1. **欄位過濾**：結構穩定、欄位有版本管理時，用允許清單留下必要欄位；注意結構變動可能讓清單漏值。
2. **任務導向摘要**：欄位或格式不穩定時，壓縮成所需資訊，並驗證金額、狀態等關鍵值及來源；代價是額外處理與可能的摘要失真。
3. **參照間接**：原文很大、當下大多用不到時，外存完整資料，只提供可回查識別碼；需要細節時再定向讀取。

記錄裁掉了哪些欄位與原始資料位置，才能在下游缺資料時辨認是否過度裁切。法規逐字證據、不可再取得的觀察或稽核資料，不能只留下不可驗證的短摘要。

冗長工具結果或子代理原文也可能把關鍵發現埋在聚合輸入中段，形成「迷失在中間」(Lost in the Middle)的風險；這是位置效應，不等於模型必然看不到中段。聚合時把關鍵發現置前，詳細結果以明確小標題分區。上游代理宜回傳結論、關鍵事實、來源位置、日期或觀察時間、方法限制與相關度，而非整段推理過程；「未找到」與「未查」須分開標示，以免下游誤把調查缺口當作否定證據。

若下游只剩少量上下文預算，不要直接交付上游的長篇研究逐字稿。以下是**示意的短交接封包**，不是 SDK 的固定欄位；短引文及分數都要對應到同一項發現，分數只是本任務的排序訊號，不能取代來源核對：

| 欄位 | 上游回傳示例 | 下游怎麼用 |
| --- | --- | --- |
| 關鍵事實與短引文 | `A-71 金額為 NT$2,480`；短引文「付款總額 NT$2,480」 | 用短引文核對事實，不帶入整頁原文 |
| 來源與時間 | `訂單查詢／A-71／付款欄位`；本次查詢時間 | 必要時按位置回查原始紀錄 |
| 相關性分數 | `0.92`（上游依「能否判斷 A-71 退款金額」給的示意分數） | 在預算不足時優先保留高相關項；不當成事實可信度 |
| 方法與缺口 | 查詢付款欄；退款政策**未查** | 下游不可把「未查」說成「沒有退款規定」 |

上游仍須保留可回查的完整來源；若退款政策尚未查，交接封包要明說缺口或請求補查。若查過卻沒有找到，應另標**已查未找到**並記錄查詢範圍，兩種狀態不能合併。

### 範例：兩張訂單的一次請求

顧客說：「A-71 付款 NT$2,480，希望週五前退回原卡；B-24 想知道是否出貨。」應用程式先保存原話，並以訂單查詢核實 A-71 的付款金額、以物流查詢核實 B-24 的出貨狀態，再把兩個訴求分開。以下是**示意狀態**，並非可直接送出的 API JSON：

```yaml
case_facts:
  A-71:
    amount: {value: "NT$2,480", source: "訂單查詢", checked_at: "本次查詢時間"}
    customer_expectation: "週五前退回原卡"
    company_commitment: null
  B-24:
    shipping_status: {value: "已出貨", source: "物流查詢", checked_at: "本次查詢時間"}
issues:
  A-71: {status: "退款資格待核對", next: "查政策與處理進度"}
  B-24: {status: "已查到出貨", next: "必要時重查物流"}
```

下次請求須實際放入相關案件事實、問題狀態、近期原話與「答覆前核對事實；`null` 不得補值」的指示。顧客的週五期待**不是**公司已承諾的期限；代理可說「已記下您的期待，是否能在週五前完成仍待確認」，不能把期待說成保證。若新的訂單結果與 NT$2,480 不符，先回查來源、記錄衝突與更正，再更新下一輪輸入；單改敘事摘要不會修正案件事實。

**檢查理解**：第 30 輪只記得「顧客想折扣」，分不清 12% 或 NT$120，應延長摘要嗎？不夠。回查原始回合，擷取精確條件與來源到案件事實區，驗證後注入下一次請求；摘要只保留談判脈絡。
